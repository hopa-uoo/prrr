БЭКЕНД: С ЧЕГО НАЧАТЬ

Пока что всё наше приложение работает в браузере:
данные лежат в localStorage, и у каждого устройства они свои.
Бэкенд нужен, чтобы данные жили на сервере и были общими.


ЧАСТЬ 1: КЛИЕНТ И СЕРВЕР


Клиент — это то, что видит пользователь (наш сайт в браузере).
Сервер — это программа на чужом компьютере, которая хранит данные
и отвечает на запросы.

Схема:
  Браузер  --(запрос)-->  Сервер  --(запрос)-->  База данных
  Браузер  <--(ответ)---  Сервер  <--(данные)--  База данных

Клиент НЕ имеет прямого доступа к базе.
Он просит сервер, а сервер решает, можно ли это делать.


ЧАСТЬ 2: HTTP — ЯЗЫК ОБЩЕНИЯ


Запрос состоит из:
  - адреса (URL): https://api.example.com/deadlines
  - метода (что хотим сделать)
  - заголовков (служебная информация, например кто мы)
  - тела (данные, если они нужны)

Основные методы:

  GET     — получить данные       (прочитать список)
  POST    — создать новое         (добавить дедлайн)
  PATCH   — изменить часть        (поменять статус)
  PUT     — заменить целиком
  DELETE  — удалить

Примеры адресов для нашего приложения:

  GET    /deadlines          — все мои дедлайны
  POST   /deadlines          — создать дедлайн
  PATCH  /deadlines/42       — изменить дедлайн с id 42
  DELETE /deadlines/42       — удалить его

Коды ответа (самые важные):

  200 — всё хорошо
  201 — создано
  400 — клиент прислал что-то не то (ошибка в данных)
  401 — не авторизован (не вошёл)
  403 — вошёл, но нельзя (нет прав)
  404 — не найдено
  500 — ошибка на сервере


ЧАСТЬ 3: JSON — ФОРМАТ ДАННЫХ


По сети данные летают текстом. Самый популярный формат — JSON.
Он очень похож на объекты JavaScript.

{
  "id": 42,
  "subject": "История",
  "title": "Эссе про реформы",
  "date": "2026-11-07",
  "time": "08:00",
  "status": "todo"
}

Список — это массив таких объектов:

[
  { "id": 42, "subject": "История" },
  { "id": 43, "subject": "Физика" }
]

Перевод туда и обратно мы уже знаем:
  JSON.stringify(объект) — объект в строку
  JSON.parse(строка)     — строку в объект


ЧАСТЬ 4: ЗАПРОС ИЗ БРАУЗЕРА (fetch)


// Получить список
const response = await fetch('https://api.example.com/deadlines', {
    headers: { 'Authorization': 'Bearer ТОКЕН' }
});
const deadlines = await response.json();

// Отправить новый
await fetch('https://api.example.com/deadlines', {
    method: 'POST',
    headers: {
        'Content-Type': 'application/json',
        'Authorization': 'Bearer ТОКЕН'
    },
    body: JSON.stringify({
        subject: 'История',
        title: 'Эссе',
        date: '2026-11-07',
        time: '08:00'
    })
});

async/await — это про «подожди ответа, не замораживай страницу».
Обычный fetch без await вернёт не данные, а обещание (Promise).


ЧАСТЬ 5: БАЗА ДАННЫХ И SQL


База данных — это таблицы, похожие на Excel.
Строка = одна запись, столбец = одно поле.

Таблица deadlines:

  id | user_id | subject  | title        | date       | status
  ---+---------+----------+--------------+------------+-------
  42 | 1       | История  | Эссе         | 2026-11-07 | todo
  43 | 1       | Физика   | Лабораторная | 2026-11-10 | done

Основные команды SQL:

-- Прочитать
SELECT * FROM deadlines WHERE user_id = 1;

-- Добавить
INSERT INTO deadlines (user_id, subject, title, date, status)
VALUES (1, 'История', 'Эссе', '2026-11-07', 'todo');

-- Изменить
UPDATE deadlines SET status = 'done' WHERE id = 42;

-- Удалить
DELETE FROM deadlines WHERE id = 42;

-- Сортировка и фильтр
SELECT * FROM deadlines
WHERE user_id = 1 AND status != 'done'
ORDER BY date ASC;

WHERE — это фильтр. ORDER BY — сортировка. ASC — по возрастанию.


ЧАСТЬ 6: АВТОРИЗАЦИЯ (КТО ТЫ ТАКОЙ)


Зачем: чтобы у каждого пользователя были СВОИ дедлайны.

Как это устроено:

  1) Пользователь регистрируется: почта + пароль
  2) Пароль НИКОГДА не хранится как есть — только его хеш
     (необратимая «подпись», по которой нельзя восстановить пароль)
  3) При входе сервер проверяет пароль и выдаёт ТОКЕН
  4) Клиент прикладывает токен к каждому запросу:
       Authorization: Bearer <токен>
  5) Сервер по токену понимает, кто это, и отдаёт только его данные

Никогда не доверяй клиенту:
  - «я отправил user_id = 5» — это можно подделать
  - сервер сам берёт user_id из токена, а не из тела запроса


ЧАСТЬ 7: ЧТО ДАЁТ SUPABASE


Supabase — это готовый бэкенд поверх настоящего PostgreSQL.

Что внутри:
  - база данных (PostgreSQL, обычный SQL)
  - регистрация и вход (Auth) с проверкой пароля и токенами
  - автоматический REST API к таблицам
  - Row Level Security (RLS) — правила вида
    «пользователь видит только строки со своим user_id»

Почему для первого курса это удобно:
  - не нужно поднимать и обслуживать сервер
  - SQL и база — настоящие, всё переносимо
  - бесплатный тариф

Важно про ключи:
  - anon/public ключ можно держать во фронтенде — он безопасен
    ТОЛЬКО вместе с RLS
  - service_role ключ — СЕКРЕТНЫЙ, только на сервере,
    ни в коем случае не в браузере

ЧАСТЬ 9: СЛОВАРИК


API     — набор адресов, по которым клиент общается с сервером
REST    — стиль API: адреса = ресурсы, методы = действия
JSON    — текстовый формат данных
токен   — «пропуск», подтверждающий, что ты вошёл
хеш     — необратимое преобразование пароля
RLS     — правила доступа к строкам таблицы
CRUD    — Create, Read, Update, Delete (создать/прочитать/изменить/удалить)
деплой  — публикация кода на сервере, чтобы он был доступен в интернете
